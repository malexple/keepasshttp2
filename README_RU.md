# KeePassHttp2

Плагин для KeePass 2.x, реализующий протокол KeePassXC-Browser (обмен
ключами crypto_box + шифрованные JSON-сообщения по локальному
WebSocket), собранный как единая самодостаточная управляемая .NET-сборка.

## Почему так вышло / история

Проект начинался как попытка написать слой криптографии/транспорта на
Zig и вызывать его из C# через P/Invoke. От этого подхода отказались в
пользу полностью managed-реализации на .NET: никаких нативных DLL,
никаких NuGet-пакетов в самом плагине — итоговый `KeePassHttp2.dll` не
имеет внешних зависимостей, кроме самого KeePass и .NET Framework.

Ни один существующий плагин не реализует этот NaCl-протокол для
классического KeePass 2.x — ближайший аналог, `keepass-natmsg`, только
пересылает трафик Native Messaging, но не говорит на самом протоколе.
У KeePassXC вообще нет системы плагинов (архитектурное
решение их разработчиков), поэтому этот плагин никогда не получится
портировать под KeePassXC — там просто нет точки расширения, куда его
можно было бы подключить.

## Архитектура

```
src/KeePassHttp2/
  Crypto/NaClBox.cs       crypto_box (X25519 + XSalsa20-Poly1305) на основе
                          вендоренных примитивов Chaos.NaCl
  Json/                   собственный JSON-парсер и writer (без System.Text.Json)
  Transport/              WebSocketServer на основе System.Net.HttpListener
  Protocol/               разбор envelope, DTO внутренних сообщений, защита
                          от replay по nonce, настройки плагина, лог плагина
  UI/                     AssociateDialog (подтверждение сопряжения),
                          OptionsDialog (порт / разрешённые Origin)
  Vendor/ChaosNaCl/       вендоренные примитивы NaCl (Curve25519, Salsa20,
                          Poly1305) — как исходный код, не как NuGet-пакет
  KeePassHttp2Ext.cs      точка входа KeePass.Plugins.Plugin
```

Каждый слой, кроме самого `KeePassHttp2Ext.cs`, покрыт xUnit-тестами в
`tests/KeePassHttp2.Tests/`: официальные тест-векторы (крипто), реальные
перехваченные сообщения (протокол), настоящий `ClientWebSocket`
(транспорт). У `KeePassHttp2Ext.cs` (диалоги, доступ к KeePassLib) нет
автоматического покрытия — для этого нужен живой процесс KeePass с
открытой базой, что выходит за рамки `dotnet test`. Проверяется вручную
через `test_orchestrator_client.py`.

## Сборка

```powershell
cd src/KeePassHttp2
dotnet build
```

Проект ссылается на локальный `KeePass.exe` только на этапе компиляции
(чтобы разрешить типы `KeePass.Plugins`/`KeePassLib` — `Private=false`,
поэтому файл не копируется в выходную папку). Если ваша установка
KeePass лежит не по пути, зашитому по умолчанию в `KeePassHttp2.csproj`,
переопределите его:

```powershell
dotnet build -p:KeePassDir="C:\Путь\К\Вашему\KeePass"
```

`global.json` фиксирует точную версию .NET SDK, под которую собирается
проект (`rollForward: disable` — при другой версии SDK сборка просто
откажется собираться, а не тихо соберётся другими байтами).

### Воспроизводимая сборка / проверка релиза

`KeePassHttp2.csproj` задаёт `Deterministic`, `ContinuousIntegrationBuild`
и `PathMap` — без единого NuGet-пакета, это обычные переключатели
MSBuild/Roslyn. При одинаковом исходном коде и точной версии SDK из
`global.json` любой должен получить побайтово идентичную DLL:

```powershell
dotnet build src\KeePassHttp2 -c Release
Get-FileHash src\KeePassHttp2\bin\Release\net48\KeePassHttp2.dll -Algorithm SHA256
```

К каждому релизу должен прилагаться `SHA256SUMS.txt` с хешем
опубликованной DLL — тогда любой, кто соберёт проект из тегированного
исходного кода, сможет убедиться, что его сборка совпадает с
опубликованной, то есть что опубликованный бинарник не подменили и не
собрали из другого кода.

## Установка

Скопируйте `bin\Debug\net48\KeePassHttp2.dll` (или `Release`, если
собирали эту конфигурацию) в папку `Plugins` вашего KeePass и
перезапустите KeePass. Плагин должен появиться в `Tools > Plugins`, а в
самом меню `Tools` появится пункт **"KeePassHttp2 Options..."**.

Если плагин вообще не появился (без ошибок, просто отсутствует в
списке) — проверьте поле `Product` в сведениях о версии файла DLL: оно
должно быть ровно `KeePass Plugin`, иначе KeePass молча пропускает файл
при сканировании папки. Это задаётся через
`<Product>KeePass Plugin</Product>` в csproj — не убирайте эту строку.

Мы осознанно не упаковываем плагин в `.plgx` — встроенный в KeePass
компилятор PLGX поддерживает максимум C# 5, а в этом проекте повсюду
используются `record`, `init`-свойства, nullable reference types и
современные `switch`-выражения. Переписывать всё под C# 5 только ради
упаковки в PLGX обошлось бы дороже, чем экономия от такого способа
установки по сравнению с обычной DLL.

## Настройка

`Tools > KeePassHttp2 Options...`:

- **Listen port** — по умолчанию `19455`. Применяется сразу; при смене
  порта внутренний WebSocket-сервер перезапускается без перезапуска
  самого KeePass.
- **Allowed WebSocket Origins** — через запятую, пусто = разрешить любой
  (по умолчанию). См. раздел "Известные ограничения" ниже — это более
  слабая, дополнительная проверка, а не настоящая граница доверия.

Настройки хранятся в `keepasshttp2-settings.json` рядом с DLL плагина
(не в `IPluginHost.CustomConfig` — почему, см. заголовок этого файла).

## Тесты

```powershell
cd tests/KeePassHttp2.Tests
dotnet test
```

Прогоняет весь набор (крипто-векторы, JSON-парсер/writer, валидация
envelope протокола, хендшейк/закрытие/shutdown/отказ по Origin
транспорта, защита от replay по nonce) — живой процесс KeePass для этого
не нужен.

## Диагностика

У плагина нет консоли (KeePass — GUI-приложение), поэтому он пишет лог в
`keepasshttp2.log` рядом с `KeePass.exe`.

**Этот лог осознанно минимален.** В нём никогда нет: полного
JSON-запроса/ответа, содержимого расшифрованной полезной нагрузки, URL
из запросов get-logins (это история посещений сайтов), полного
`clientID` или паролей. Если этот файл когда-нибудь прочитает кто-то
посторонний — максимум, что он узнает, это "в момент Y кто-то подключился
и сделал X", а не какие сайты вы посещали и что было в сообщениях. Единственное
осознанное исключение — журнал `associate`/`test-associate` (какое имя
использовалось при сопряжении, когда) — это не утечка, а фича: она
позволяет заметить неожиданное сопряжение в собственном логе.

## Ручная сквозная проверка

`test_orchestrator_client.py` проводит полный реальный хендшейк с
работающим плагином: `change-public-keys` → `test-associate` (ожидается
отказ, пары ещё нет) → `associate` (всплывает настоящий диалог
Allow/Deny в KeePass — нажмите Allow, чтобы увидеть весь успешный путь)
→ `test-associate` снова (теперь успешно) → шифрованный `get-logins` →
проверка повторной отправки nonce (должна быть тихо отклонена).

```powershell
pip install websockets pynacl
python test_orchestrator_client.py
```

## Статус протокола

Реализовано:
- `change-public-keys` (обмен эфемерными сессионными ключами)
- `associate` / `test-associate` (постоянное сопряжение через диалог с
  подтверждением человеком, хранится в `CustomData` открытой базы)
- `get-logins` (шифрованный, ищет по открытой базе по хосту из URL)
- Защита от replay по nonce (для каждого clientID)

Пока не реализовано (отклоняется как `unhandled inner action`):
- `generate-password`, `lock-database`, `get-logins-count`

## Известные ограничения / принятые риски

Это осознанные, задокументированные компромиссы, а не недосмотры:

- **`test-associate` — это простое сравнение ключей, а не
  challenge-response.** Так работает сам настоящий протокол
  KeePassXC-Browser — в их собственной документации это отмечено как
  известная, небольшая слабость протокола. Мы не стали это "исправлять"
  сами, потому что это сделало бы нас несовместимыми с протоколом,
  который мы реализуем.
- **Allow-list по Origin защищает только настоящие браузеры, но не
  локальные процессы.** Браузер не может подделать собственный заголовок
  `Origin`; любая другая локальная программа может выставить туда что
  угодно — это просто ещё один HTTP-заголовок под её контролем.
  Настоящая граница доверия — это диалог Allow/Deny в `associate`, а не
  фильтрация по Origin.
- **У `associate`/`test-associate` сейчас нет автоматического тестового
  покрытия.** Для них нужен живой процесс KeePass с открытой базой и
  человек, кликающий в настоящем диалоге — проверяется вручную через
  `test_orchestrator_client.py`, а не через `dotnet test`.
- **Идентификационные ключи клиентов хранятся в `CustomData` базы в
  открытом виде (base64).** Это соответствует дизайну самого протокола;
  любой, у кого есть доступ на чтение к расшифрованному содержимому
  `.kdbx`-файла (то есть кто уже мог бы открыть базу), увидит, какие
  клиенты сопряжены.
- **При смене порта через диалог настроек есть короткое окно гонки**:
  в момент, когда `HttpListener` на старом порту закрывается, а новый
  ещё запускается, попытка подключения может получить непоследовательный
  ответ вместо чистого отказа. Повторное подключение через секунду
  проходит нормально. Не относится к безопасности, просто небольшая
  шероховатость при ручной смене настроек.

## Запланировано / дальнейшая работа

- Своё минималистичное браузерное расширение (отдельный проект, один
  исходный код, собираемый под разные браузеры через инструмент вроде
  `wxt.dev`), говорящее по этому протоколу напрямую через WebSocket на
  JS (`tweetnacl-js` для crypto_box) — настоящее расширение
  KeePassXC-Browser нельзя направить на этот плагин, так как оно умеет
  только Native Messaging, а не сырой WebSocket.
